# Production на Layero

Актуальность исследования: 12 октября 2026. Реальный деплой в рамках задачи не выполнялся.

## Подтверждённая модель платформы

По официальной документации Layero:

- Node.js HTTP-приложение запускается как runtime `node_web`.
- Layero использует готовый runtime-шаблон контейнера; собственный Dockerfile для этого проекта не требуется.
- Приложение должно слушать `0.0.0.0` и порт из `PORT`.
- Команда `start` может быть взята из `package.json`; в проекте это `node server/server.js`.
- Health-check ожидает ответ `GET /` без 5xx; проект также имеет `GET /api/health`.
- Переменные окружения доступны во время сборки и в runtime-контейнере.
- `.env*` нельзя коммитить; секреты задаются в панели Layero.
- GitHub push создаёт деплой; production выбирается через promote.
- HTTPS для подключённого домена выпускается платформой.
- Файловая система runtime-контейнера эфемерна.

Официальные источники:

- https://docs.layero.ru/runtime/overview/
- https://docs.layero.ru/deploys/layero-json/
- https://docs.layero.ru/deploys/env-vars/
- https://docs.layero.ru/deploys/

## Конфигурация репозитория

`layero.json` фиксирует только параметры, которые нужны этому приложению:

- runtime: `node_web`;
- start: `npm start`;
- внутренний порт: `4174`.

Node.js уже ограничен в `package.json` диапазоном `>=20 <25`. Layero требует Node.js 20 или новее.

## Переменные окружения

| Переменная | Обязательность | Назначение |
|---|---|---|
| `NODE_ENV=production` | Да | Включает production-проверки и поведение |
| `PORT` | Да, задаёт Layero | Порт HTTP-сервера |
| `ADMIN_PASSWORD` | Да | Пароль владельца, минимум 12 символов, не `admin` |
| `ADMIN_TOKEN_SECRET` | Да | Секрет подписи токенов, минимум 32 случайных символа |
| `PUBLIC_SITE_URL` | Да | Канонический HTTPS origin без завершающего `/` |
| `CORS_ALLOWED_ORIGINS` | Да | Разрешённые origin через запятую |
| `TELEGRAM_BOT_TOKEN` | Для Telegram | Секрет бота |
| `TELEGRAM_CHAT_ID` | Опционально | Резервный получатель до привязки сотрудников |
| `TELEGRAM_DISABLED=false` | Да для включения | Глобальный выключатель отправки |
| `TELEGRAM_POLLING_ENABLED=true` | Только на одной реплике | Long polling бота; на остальных `false` |
| `DATA_STORE_PATH` | Только временно | Путь к JSON. Не превращает эфемерный диск в постоянный |
| `VITE_API_URL` | Обычно пусто | Публичный API origin; при одном домене используется same-origin |

Секреты нельзя помещать в `VITE_*`: Vite встраивает их в клиентский bundle.

## Критический блокер данных

Сейчас проект записывает:

- заказы, пользователей, каталог и настройки в JSON по `DATA_STORE_PATH`;
- загруженные изображения в `public/uploads`.

На Layero эти файлы могут исчезнуть после остановки, пересборки или смены контейнера. До реального запуска необходимо:

1. Перенести структурированные данные в PostgreSQL. Layero предоставляет `LAYERO_DATABASE_URL`, но база отмечена платформой как beta; допустима и внешняя управляемая PostgreSQL.
2. Перенести изображения в S3-совместимое object storage/CDN.
3. Добавить миграцию текущего JSON и проверку количества записей.
4. Настроить автоматический backup базы и retention object storage.
5. Провести восстановление на отдельном окружении.

Без этого production можно использовать только как демонстрационный стенд без реальных заказов.

## Первый деплой после устранения блокера

1. Подключить GitHub-репозиторий в Layero.
2. Проверить plan через `npx layero@latest deploy --dry-run`.
3. Добавить переменные окружения в панели.
4. Деплоить отдельную ветку как preview.
5. Проверить `/api/health`, главную, admin login, загрузку, создание тестового заказа и Telegram.
6. Перезапустить runtime и подтвердить, что заказ и изображение сохранились.
7. Только после backup/restore smoke выполнить promote в production.

## Обновление

1. Создать ветку и получить preview-деплой.
2. Выполнить тесты и миграции на копии данных.
3. Снять backup перед promote.
4. Promote только проверенного deploy id.
5. Проверить health, заказ, admin и Telegram после переключения.

## Откат

1. Откатить production на предыдущий успешный deploy через Layero rollback/promote.
2. Не откатывать базу автоматически вместе с кодом.
3. Если миграция несовместима, использовать заранее подготовленный down-план или восстановление в новую базу.
4. После отката проверить `/api/health`, чтение заказов и Telegram outbox.

## Наблюдаемость

- Контролировать `/api/health` и 5xx.
- Не логировать токены, пароли и полные персональные данные.
- Следить за Telegram outbox и конфликтом `getUpdates`.
- Для нескольких реплик оставить polling включённым только у одной.
- Хранить резервные копии вне runtime-контейнера.
