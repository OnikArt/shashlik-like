# Checkpoint 6 — подготовка без изменений production

## Защита заказов: требуется согласовать миграцию

Сейчас `app_state` хранит всё состояние в одной JSONB-записи. `mutateStore` сериализует записи только в одном процессе Node.js; два экземпляра могут прочитать одну версию и перезаписать изменения друг друга. Поэтому хранение ключа только в JSON заказа не даёт гарантии для одновременных запросов и нескольких экземпляров.

Предлагаемая миграция: отдельная таблица `order_idempotency` с уникальным `key`, SHA-256 хэшем канонизированного запроса, `order_id`, сохранённым ответом и временем создания; для `app_state` — механизм контроля версии или единая транзакционная блокировка всех операций записи. Порядок: сделать проверенную резервную копию PostgreSQL и медиа; проверить её восстановление отдельно; выполнить миграцию в тестовой базе; обновить все пути записи состояния; проверить конкурентные запросы из двух процессов; лишь затем согласовать production-миграцию. Откат приложения после применения новой схемы должен сохранять новые столбцы и таблицу; удаление таблицы при откате запрещено.

Клиент создаёт случайный ключ на одну попытку оформления и хранит его до подтверждённого ответа. Сетевой повтор использует тот же ключ и тот же снимок запроса. Изменение формы или корзины создаёт новый ключ. API принимает заголовок `Idempotency-Key` (старые клиенты без заголовка работают по прежнему контракту). При совпадении ключа и хэша API возвращает исходный номер и tracking token без повторных уведомлений и события `order_created`; при другом хэше возвращает 409. Сохранение заказа и записи ключа выполняется атомарно до отправки уведомлений. Следует проверить поведение при сбое после commit, при двух одновременных запросах и при перезапуске сервера.

## Яндекс Метрика — план включения

Счётчик не добавлен. После предоставления ID и согласия на отправку обезличенных коммерческих событий: загрузить официальный скрипт только на публичных страницах, включить ecommerce, передавать `view_item` при открытии товара, `add_to_cart` после добавления, `begin_checkout` при переходе к оформлению, `promo_applied` только после успешного ответа сервера на проверку кода, `purchase` только после ответа 201 или идемпотентного повторного ответа о ранее созданном заказе. Для `purchase` использовать стабильный номер заказа, стоимость, валюту RUB и товарные ID; повторный ответ не должен повторно отправлять событие в рамках сессии. Не отправлять имя, телефон, адрес, комментарий, tracking token и URL страницы заказа. Сначала проверить события в тестовом счётчике и согласовать cookie/privacy-текст.

Внутренняя аналитика уже фиксирует `product_view`, `add_to_cart`, `checkout_started` и серверное `order_created`. Успешное применение промокода как отдельное событие отсутствует. Переход в checkout не считается покупкой.

## Безопасная проверка и публикация

1. После согласования миграции поднять отдельную тестовую PostgreSQL с синтетическими заказами и отключёнными Telegram/MAX.
2. Проверить один заказ, быстрый двойной клик, последовательный повтор HTTP, конфликт тела, параллельные запросы из двух процессов, сбой после сохранения, перезапуск, скидку, бесплатную доставку, ошибки и ровно одно событие/уведомление на заказ.
3. Перед публикацией получить полную проверенную резервную копию `app_state`, `app_media` и `public/uploads`, сохранить контрольные суммы и текущий git commit. Не использовать локальный `store.json` как production-копию.
4. Выполнить миграцию только с отдельным разрешением и в согласованное окно, затем деплой конкретного commit. Проверить `/api/health`, каталог, оформление тестовым режимом без доставки реальным получателям, админ-панель и очереди уведомлений.
5. При ошибке вернуть прежний commit приложения; данные и новую схему не удалять. Если состояние БД требуется восстановить, сначала остановить приём новых заказов и согласовать восстановление с учётом заказов, созданных после копии.
