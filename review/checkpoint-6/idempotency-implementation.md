# Локальная реализация идемпотентности заказов

## Изоляция испытаний

Использован отдельный PostgreSQL 18.1 в `/private/tmp/shashlik-idempotency.Hzl2XB/data`. Он запущен с `listen_addresses=''`, доступен только по Unix-сокету в той же временной папке. Финальная схема проверена в чистой тестовой базе `shashlik_idempotency_test_v3`, отдельно от любых пользовательских и production-баз. Тест перед записью проверяет имя БД, отсутствие TCP-адреса сервера и точный путь каталога кластера. Данные заказов и пароль администратора в тесте синтетические. Telegram подменён локальным HTTP-моком, MAX отключён.

## Новая схема и порядок работы

Миграция: `scripts/migrations/2026-11-12-order-idempotency.sql`. Таблица `order_idempotency` хранит уникальный ключ, SHA-256 от канонизированного JSON запроса, ID заказа, исходный публичный ответ и время создания. Ключ и заказ фиксируются одной транзакцией PostgreSQL под блокировкой строки `app_state`. Вне транзакции уведомления отправляются только для нового заказа. Повтор с теми же данными возвращает сохранённый ответ 201; изменение данных с прежним ключом даёт 409. Клиент сохраняет ключ и точное тело запроса в памяти формы до успешного ответа, поэтому повтор после сетевого сбоя использует тот же ключ. Клиенты без заголовка `Idempotency-Key` продолжают работать.

Другие записи в `app_state` защищены сравнением `updated_at` перед обновлением: устаревший снимок не перезапишет новый заказ. Для нормализации читаемого состояния добавлен ограниченный повтор при конфликте версии. Некоторые административные операции, которые читают и пишут состояние вне `mutateStore`, при конфликте могут получить ошибку вместо автоматического повтора; это безопаснее потери заказа, но требует отдельного устранения до многопроцессного production-запуска.

## Проверенные случаи

Автоматический тест `tests/idempotency-postgres.test.js` проверяет создание, последовательный повтор, конфликт другого тела, параллельные запросы в одном и двух процессах, сетевой тайм-аут, принудительное завершение первого процесса после commit, сохранность заказа и отсутствие новой попытки уведомления при HTTP-повторе. Он также проверяет старый API без ключа и изменение статуса заказа в админ-панели. Файловое хранилище проверяется отдельным тестом в `tests/server.test.js`. PostgreSQL перезапущен вручную: количество записей идемпотентности до и после совпало.

## Граница гарантии внешних уведомлений

Идемпотентность исключает повторное уведомление из-за повторной отправки HTTP-запроса. Она не может обеспечить строго однократную доставку в Telegram/MAX при аварии между вызовом внешнего API и записью результата: эти сервисы не подтверждают идемпотентность по ключу нашего заказа. Если процесс погиб до вызова API, заказ уже сохранён, а уведомление может отсутствовать. Для гарантированной доставки нужен отдельный транзакционный outbox и механизм сверки/ручной обработки неопределённого результата; автоматический повтор может привести к дублю, если внешний сервис получил сообщение перед сбоем.

## Внедрение и откат

Никаких production-действий не выполнено. Перед будущим деплоем нужны проверенная резервная копия `app_state`, `app_media`, uploads, тестовое восстановление и отдельное разрешение на production-миграцию. Миграция должна выполняться до запуска новой версии. На время переключения нельзя одновременно принимать заказы старой и новой версией, так как старая версия не использует контроль версии. После запуска проверить health, повтор запроса с одним ключом, уведомления и админ-панель.

При ошибке вернуть предыдущий commit приложения, сохранив таблицу `order_idempotency` и данные. Файл `scripts/migrations/2026-11-12-order-idempotency-rollback.sql` сознательно не удаляет таблицу. Возврат данных БД из резервной копии требует отдельного решения с учётом заказов, созданных после копирования.
