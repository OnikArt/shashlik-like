# Checkpoint 7 — готовность к Layero

**Статус: BLOCKED для публикации.** Локальные проверки пройдены, но фактическое production-хранилище, резервная копия и настройки приложения в панели Layero не подтверждены. Рабочая БД, GitHub и production не изменялись.

## Фактическая конфигурация в репозитории

- `layero.json`: `runtime=node_web`, Node 22, `npm ci --include=dev`, отдельный `npm run build`, затем `node server/server.js`, порт 4174. Dockerfile и `.dockerignore` отсутствуют. Реальный способ сборки и переменные в панели Layero недоступны; нужно сверить их с этим файлом.
- Сервер слушает `0.0.0.0:${PORT || 4174}`. HTTP bind происходит до инициализации PostgreSQL. `/health` и `/api/health` возвращают 200 только при готовом frontend и хранилище; при проблеме БД — 503.
- В production обязательны `PUBLIC_SITE_URL`, `ADMIN_PASSWORD` (не менее 12 символов), `ADMIN_TOKEN_SECRET` (не менее 32 символов) и `LAYERO_DATABASE_URL` либо `DATABASE_URL`. Дополнительно проверить `DATABASE_SSL`, Telegram/MAX переменные, `TELEGRAM_POLLING_ENABLED`, `CORS_ALLOWED_ORIGINS` и `DATABASE_CONNECTION_TIMEOUT_MS`. Значения секретов в отчёт не включены.
- Данные заказов, товаров, настроек, пользователей и outbox находятся в `app_state.data` (JSONB); загруженные через новый PostgreSQL-путь изображения — в `app_media.bytes`; ключи заказов — в `order_idempotency`. Старый файловый режим хранит `store.json` и `public/uploads` вне PostgreSQL. Наличие файлов в действующем production не установлено.
- Сервер сам создаёт `app_state` и `app_media`, но **не** запускает миграцию `order_idempotency`; отсутствие таблицы блокирует готовность. Пустая PostgreSQL в production блокируется без `ALLOW_EMPTY_DATABASE_INITIALIZATION=true` — включать его для действующего сайта нельзя.

## Найденное и исправленное

- В `server/server.js` добавлен `Cache-Control`: файлы сборки с хешем — год и `immutable`, HTML — `no-cache`, остальные статические файлы — один час. Это безопасная локальная правка производительности; после неё отдельная контейнерная проверка не проводилась.
- Недостаточно проверить только наличие `order_idempotency`: при несовместимой структуре таблицы старт пройдёт, а заказ может завершиться ошибкой. Перед публикацией сравнить структуру и права на таблицу с миграцией на копии production.
- `npm ci` предупредил о postinstall-скриптах `esbuild` и `fsevents`, но сборка прошла. Убедиться, что Layero применяет совместимый npm и Node 22.
- Уведомления не обладают строгой гарантией однократной доставки при сбое между commit БД и внешним API. Повтор HTTP-запроса уведомления не дублирует. После обновления страницы клиент может создать новый ключ; это оставшийся риск повторного логического заказа.

## План публикации (только после отдельного разрешения)

1. В панели Layero зафиксировать текущий commit/версию, runtime, Node, Build/Start commands, PORT, health path, attached PostgreSQL и volume. Подтвердить, откуда действующая версия читает заказы и изображения: `store.json`/uploads либо PostgreSQL. Не использовать каталог как резервную копию.
2. Получить полный снимок этого источника: для PostgreSQL — `pg_dump -Fc` плюс отдельно файлы, если есть; для файлового режима — оригинальные `store.json` и `public/uploads` с путями. Сохранить версии конфигурации и кода, зашифровать архив, посчитать SHA-256 и сравнить число заказов, товаров, сотрудников, изображений и настроек.
3. Восстановить production-копию в **отдельной** среде и проверить состав, права, доступность изображений, контрольные суммы. Пока это недоступно, не продолжать переключение.
4. Согласовать окно без приёма заказов; после остановки записи снять финальный инкремент/полный архив и сверить число заказов. При файловом источнике импортировать архив и изображения в PostgreSQL только по отдельному разрешению; проверить целостность до смены backend.
5. Применить SQL миграции идемпотентности к подготовленной PostgreSQL отдельно от старта приложения; проверить таблицу, ограничения, права и отсутствие потери строк. `ALLOW_EMPTY_DATABASE_INITIALIZATION` оставить выключенным.
6. Сверить обязательные переменные без вывода значений. Build: `npm run build`; Start: `node server/server.js`. Не собирать при старте. Не допускать одновременной обработки заказов старым и новым backend.
7. Развернуть новую версию, проверить `/api/health` = 200 и `storage=postgres`, каталог/цены, изображения, админку, сохранённые заказы и статусы. Проверить Telegram/MAX в согласованном тестовом канале; затем наблюдать ошибки, 503, задержки БД и outbox.

## Откат

1. При ошибке остановить приём новых заказов и сохранить новый снимок БД; не удалять `order_idempotency` и не откатывать БД вслепую.
2. Вернуть предыдущую версию приложения и прежние настройки подключения только после сверки, что она читает тот же полный набор данных. Старый код может не поддерживать новый механизм контроля записи; нельзя запускать его параллельно с новым.
3. Если нужен возврат к файловому хранилищу, сначала обеспечить перенос заказов, созданных после переключения. Восстановление старого архива без финальной синхронизации приведёт к потере этих заказов.
4. Проверить `/api/health`, каталог, заказы и изображения; сохранить копии обоих состояний для разбора.

## Что необходимо подтвердить в Layero

Текущий источник данных и volume, доступность оригинального production-архива, текущий commit, фактические команды и Node, путь health check, переменные окружения, доступ к `pg_dump`/импорту, возможность окна без записи и план переключения. Без этих сведений публикация заблокирована.
